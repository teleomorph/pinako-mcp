## Findings surfaced this session

  commit `d22d751`'s `PASS HTML RAW` directive. Re-verified end-to-end
  on Haiku 4.5 (raw `<p>...</p>` content stored, NO entity escapes).
  Tracked in `docs-archive/agentic-ai-pre-ship-fixes.md#12` (archived
  2026-05-23 alongside the retired `native-chat-test-findings.md`;
  slim summary in `ai-resolved.md`).
- **NEW FINDING — bulk_apply description doesn't match engine envelope
  scope enforcement.** Surfaced by C7. The description at line 987 of
  `supabase/functions/chat-completion/index.ts` says "set
  `scope='library' + libraryId` for library-bounded batches", but the
  engine actually requires the envelope `scope` to match the sub-ops'
  scope EXACTLY. For `delete_note` sub-ops in a library, sub-op scope
  is `library-notes`, so envelope scope must also be `library-notes`
  — not `library` (would fail BULK_SCOPE_MISMATCH). User-facing
  impact: when a real user asks for a batch note-delete via chat,
  Haiku emits the bulk_apply WITHOUT envelope scope at all (defaults
  to `tree`), and the chat panel's approval card injects
  `confirmedByUser:true` on sub-ops but does NOT add envelope
  `scope`/`libraryId`. Result: the bulk would fail at the engine
  scope-mismatch check after the user already approved. Tracked in
  `docs-archive/agentic-ai-pre-ship-fixes.md#11` (archived 2026-05-23
  alongside the retired `native-chat-test-findings.md`; slim summary
  in `ai-resolved.md`).
- **Cross-scope downstream routing not exercised in C2.** C2's user data
  happens to have zero cross-scope URL overlap. To validate the
  "MUST group by sourceScopes[]" directive, seed bookmarks data first
  (C2-bis exercised this in 2026-05-21 — see additional findings below).
- **C5 (batch tag) deferred.** Requires tab-seeding infrastructure
  that doesn't exist (no `create_tab` engine tool; tabs come from
  real Chrome windows). Logging here so future session knows to
  scope this differently (e.g., test against existing library

- **~~EF deploy verification (Step 1) — STALE (RESOLVED 2026-05-21)~~.**

- **~~Tool description alone doesn't steer cross-library fallback (RESOLVED 2026-05-21)~~.**
  C7-bis Run 1 showed even with the explicit "DO NOT keep retrying
  bulk_apply" directive in the tool description, Haiku 4.5 retried
  with different envelope shapes after each engine rejection.
  Description sets intent, engine error message drives recovery.
  Sharpened `BULK_LIBRARY_MISMATCH` to explicitly say "Fall back to N

  future audit. Engine-error-message audit done 2026-05-21
  (continuation) — no other engine codes had the same load-bearing
  gap; BULK_SCOPE_MISMATCH could be defensively sharpened but the
  cross-library case is already caught by BULK_LIBRARY_MISMATCH first
  in the common envelope shape. Filed YAGNI.
- **C2-tris finding #1: agent paraphrased bookmark-deletion safety
  warning** instead of using the verbatim text in system prompt §6.
  Spec says "MUST surface this warning verbatim." Agent rewrote into
  a similar but non-identical sentence. Worth a system prompt sharpen:
  emphasize "VERBATIM" more strongly or quote the exact string with
  a hard-stop marker. Non-blocking.
- **C2-tris finding #2: agent asked "should I proceed?" in reply text**
  instead of letting the chat panel's approval card handle consent.
  System prompt §6 explicitly says "DO NOT ask the user for approval
  in your reply" — narrate intent and call the tool. Real chat panel
  WOULD have shown an approval card for the 4× delete_node sub-ops,
  so the agent's text-side ask is redundant and against discipline.
  Worth a system prompt sharpen + maybe an explicit "do not write
  'should I proceed' / 'do you want me to' / 'shall I' phrases".
  Non-blocking.
- **C2-tris finding #3: agent used 4× parallel `delete_node` instead
  of `bulk_apply`** at the 4-target threshold. The cheatsheet says
  "Use bulk_apply ONLY when applying the same op to 4 OR MORE
  targets". 4 destructive same-op targets = bulk_apply preferred.
  Agent chose individual calls. Soft violation — work got done — but
  the user loses single-undo atomicity. Possibly Haiku reads "4 OR
  MORE" as "more than 4" = 5+ (off-by-one in threshold interpretation).
  Or destructive ops are treated differently due to caution. Worth
  rewording the threshold to "4+" or "≥4" if the off-by-one read is
  the cause. Non-blocking. Tracked in `ai-todo.md#33`
  (migrated 2026-05-23 from the retired `native-chat-test-findings.md`).
- **C10 finding: agent cited an anchor ID (`#guide-library-groups`)

  anchor ids back to the user". Agent extracted some anchors from the
  result set correctly (e.g. `#guide-group-nodes`) but also cited one
  it didn't get back, suggesting extrapolation from naming convention.
  Soft hallucination — not load-bearing, but worth tightening the
  cheatsheet to "CITE ONLY anchors actually present in the most
